# ADR-013: UUIDv7 for Durable Entity Identifiers

**Status:** Accepted

## Context

Entities must carry stable, cross-device identity from the moment they
are created on any node (Windows or, later, Android), before ever
touching a server. Database auto-increment IDs cannot serve as
cross-device identity — two devices creating a `Memory` offline would
collide on the same integer.

## Decision

Every durable entity ID is a UUIDv7 string (RFC 9562), generated by
`reva_core/shared/ids.py::uuid7`. No cross-device entity uses a SQLite
`ROWID`/`INTEGER PRIMARY KEY AUTOINCREMENT` as its identity.

## Alternatives considered

- **UUIDv4** — globally unique but not time-sortable, which would hurt
  index locality on ID-ordered scans and lose the free chronological
  ordering UUIDv7 provides.
- **ULID** — similar time-sortable properties to UUIDv7, but is not an
  IETF standard and would need its own third-party dependency; UUIDv7
  achieves the same property as a ~20-line stdlib-only function.
- **A third-party UUIDv7 package (e.g. `uuid6`)** — considered, but no
  concrete compatibility blocker was found for implementing it directly
  against Python 3.12's `uuid` module, so no dependency was added for
  one function (see docstring in `shared/ids.py`).

## Consequences

- IDs are naturally time-sortable, which keeps `id`-ordered SQLite
  indexes useful without a separate `created_at` index in some cases.
- Every ID contract in `shared/contracts/ids.py` validates the UUIDv7
  shape, so a UUIDv4 accidentally used as an entity ID fails validation
  immediately rather than silently working until a sync conflict
  exposes the mistake.

## Security implications

UUIDv7 embeds a millisecond timestamp in cleartext within the ID. This
is a acceptable/expected tradeoff for an internal entity identifier (it
is not a secret or a capability token); it must never be used as an
unguessable secret (e.g. a pairing token), which is a separate,
non-time-based random value by design.
