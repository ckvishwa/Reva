# PRE-00: Finance monthly plan accounting contract

Status: proposed contract and executable **test-only** reference, based on PR #33 head `129ef650f99a6da8e6921bd314e28eca65ec8906`. Design reference: PR #34, `docs/plans/REVA_Finance_Intelligence_Implementation_Preflight.md`. No `monthly_plan` Kernel query or API route exists in this slice. Passing the fixture tests does not mean the live planner works.

## Boundary and compatibility

`finance.monthly_plan` v1 is an additive read result and request shape in `contracts/finance-monthly-plan.v1.schema.json`, mirrored byte-for-byte in the spec contract directory. It does not change existing `/v1/domains/finance/*` responses, transaction signs, budget records, event schema, SQLCipher migration version, or UI contracts. Consumers must explicitly request v1 when implemented. A response includes `schema_version`, `engine_version`, date horizon, currency, `hypothetical`, provenance, assumptions, and missing inputs. Structural schema validation uses JSON Schema 2020-12 with date format checking. The future Rust implementation must enforce the semantic rules below, which JSON Schema cannot express by itself.

The current Rust `cashflow` query classifies non-transfer transactions by sign, and `account_balances` sums opening balance and transaction amounts. It cannot yet distinguish card purchases from cash expenses, linked repayments, principal from interest, or bill matching. Do not use those current aggregates as safe-to-spend. `bill.mark_paid` can optionally create a transaction; a paid bill must not be counted again. Existing `budget.set` is a category budget, not a savings commitment.

## Authoritative accounting rules

- Every authoritative amount is a signed or nonnegative 64-bit **integer minor unit** with an ISO 4217 currency. Never round silently or use binary floats. A report is for one currency; another currency is excluded with an explicit missing/unsupported conversion indicator if its value matters. No implicit FX rate.
- `cash_available_minor` is the sum of designated, confirmed spendable cash-account balances at `as_of`. Savings, credit and loan balances are not silently added to checking. Unknown or disputed opening cash balance makes cash and safe-to-spend unknown (`null`). A confirmed amount of zero is numeric `0`, not `null`.
- `confirmed_income_minor` is money already received in the selected cash accounts during the report period. `expected_income_minor` is dated, unreceived income; each paycheck is counted once when it becomes cash. Transfers between owned accounts are neither income nor expense. A liability draw is not income.
- Fixed expenses have dated obligations (rent, utilities, insurance, subscriptions); variable expenses and shocks are separately identified estimates/known costs with dated assumptions. `scheduled_obligations_minor` sums future non-debt cash expenses in the horizon, including fixture variable estimates and the unexpected cost once its date is known. It excludes paid bills, debt repayments, internal transfers and card purchases that have no immediate cash leg. Sources identify each component.
- A credit-card purchase increases liability and counts as purchase spending once. A credit-card minimum or extra repayment reduces checking and liability, and is a cash flow, but is not another purchase expense. The minimum enters `required_debt_payments_minor`; extra repayment remains in the daily projection and assumptions. A loan payment similarly reduces cash; only its principal reduces debt, while interest is a financing expense. A missing minimum makes the plan incomplete. APR is unknown in this fixture; future interest forecasting must remain unknown until debt terms exist.
- A bill matched to an imported transaction, or marked paid with a generated transaction, is one economic payment. A duplicate CSV fingerprint is rejected before planning. Import descriptions and merchants remain untrusted data and have no path to instructions, tools or permissions.
- A physical savings transfer has two ledger legs and reduces designated checking cash once. The savings goal is a commitment: before the planned transfer, the whole target is held back; after it, only the remaining virtual earmark is held back. The physical transfer is not an expense. `minimum_cash_reserve_minor` is an additional holdback, independent of the savings goal.
- Daily projected balance starts from confirmed cash at `as_of`, then applies dated cash legs in deterministic date/source order. Daily headroom is projected cash minus reserve minus the still-pending savings commitment. `minimum_projected_cash_headroom_minor` is the **minimum over all days**, not the month-end amount. `safe_to_spend_minor=max(0,min_headroom)` and `projected_shortfall_minor=max(0,-min_headroom)` only when all critical amounts are known. Thus a positive month-end balance can coexist with a shortfall.
- Status precedence: missing critical balance, date, currency, debt minimum or required obligation amount => `incomplete` with affected derived numbers `null`; otherwise negative headroom => `shortfall`; otherwise estimates/unconfirmed inputs => `provisional`; otherwise `ready`. Scenario requests add temporary dated cash flows to a copy of the projection, set `hypothetical=true`, and cannot append events or change stored records.
- `source_ids` contains contributing account, transaction, obligation and assumption IDs. Each numeric field has a `components` entry with source IDs, and each daily row carries cash-account and dated cash-flow IDs. Consumers must not present an unsupported number as a fact. The Rust implementation must reject response dates outside the requested horizon, mismatched currencies, duplicate source IDs, and arithmetic/provenance inconsistencies.

## Synthetic golden case

`tests/fixtures/finance_intelligence/november_2026.json` is entirely fictional and fixed to November 1–30, 2026. Checking begins at $500, savings at $200, card liability at $300 and loan liability at $1,000. Two expected $1,500 paychecks arrive November 8 and 22. Rent on November 2 and utilities on November 5 push checking to **-$620** before the first paycheck. Rent, utilities, insurance, groceries, transport, subscriptions and an unexpected expense total **$1,635** in non-debt outflows. Loan and card minimums total **$200**. A further $80 card repayment, $100 savings transfer, and $200 card purchase are represented with their own semantics. Checking ends at **$1,485**, card liability at **$370**, loan liability at **$880**, savings at **$300**. The $250 reserve and pending $150 savings target make minimum headroom **-$1,020**. Safe-to-spend is $0; projected shortfall is $1,020.

The fixture stores all 30 expected daily cash balances/headroom values as static golden data. The independent test-only reference recomputes them from the dated records and compares every day. The fixture also includes a paid and matched bill, duplicate import attempt, foreign-currency record, missing card minimum case, and malicious merchant text. Golden vectors and reference assertions are PRE-00 acceptance data, not generated by or proof of a production monthly planner. Tests for the future Rust/UniFFI/API implementation must consume this fixture in FIE-01/FIE-02, without relaxing these assertions.

## Security and next slice

No production storage, SQLCipher, DPAPI, Credential Manager, Android Keystore, policy broker, ADK tool registry, hosted-model flag, or permission is changed here. The test oracle reads only repository synthetic JSON. The existing capability registry still forbids payment, transfer, purchase and bank-login actions. Bookkeeping transfer records are not a funds-movement command.

**FIE-01 — Debt Terms, Income Schedules, and Obligations:** add the minimum versioned Rust event/projection model for liability type, APR/interest method, due and minimum amounts, dated expected income, obligation status and transaction match, and linked internal transfer legs. Add a reversible SQLCipher migration/backup/replay check, old-database compatibility, deterministic merge/sync semantics, and native/Python/Kotlin conformance on the synthetic fixture. Do not add the safe-to-spend query until these records and unknown-value rules are implemented and validated; dated projection belongs in FIE-02. Real Windows DPAPI and Android Keystore/device tests remain separate hardware gates.
